# IOP function-export coverage and entry-boundary audit

This read-only audit examines the current 24-module, 2,241-function Ghidra C export in `.scratch/mesh/codex-audit/iop-reloc-nextphase/decomp-gp-corrected-base0-final`. The per-module manifests, raw-input hashes, safe coverage measurements, relocation comparison, and entry-point candidates are summarized in [coverage-snapshot-20261004.json](coverage-snapshot-20261004.json). No module C body or payload bytes are copied here.

All 2,241 saved functions generated C successfully, no function entry is outside its module's `.text`, and the Ghidra `.text` block hash matches the raw ELF `.text` hash in all 24 GP-context probes. Those results establish input identity and export success for saved functions; they do not establish complete executable-text coverage. The exporter ([its source](../../../.scratch/mesh/codex-audit/iop-ghidra/scripts/ExportIopDecompilation.java)) records function entry and `body_bytes`, but it does not serialize function-body address sets, instruction/code-unit ranges, or unowned-byte ranges.

The 506,336 bytes of `.text` contain 12,488 bytes of parsed import/export tables. Summed Ghidra function body sizes are 469,428 bytes: 92.7% of all `.text`, or 95.1% after subtracting those tables. Treat these ratios as diagnostics, not coverage proof. Some modules' summed function bodies exceed `.text` after table subtraction, which shows that these totals are not the size of a disjoint, code-only address union. The largest positive aggregate differences are LGDEV (9,852 bytes), PADMAN (4,876), LOADCORE (2,808), SYSCLIB (2,080), LIBSD (1,296), and SIFMAN (860). Those are priority targets for a future address-range listing audit, not claims of that many missing instructions.

The clearest boundary gap is at the module entry points. Thirteen `.iopmod` entry offsets are zero but no saved Ghidra function starts at zero. Each offset is inside `.text`, not at a parsed import/export table header. Twelve start with a MIPS `addiu sp,sp,negative` prologue word; LOADCORE starts with `0x40806000` (a COP0 instruction), followed by the raw words `0x8c820000`, `0x00000000`, and `0x0002ed00`. The other eleven module entry offsets do have saved function starts. This makes the 13 offset-zero locations concrete function-boundary candidates. It does not prove the game invokes these modules or that the candidate's complete function extent is known. The pinned [PS2SDK Loadcore source](https://github.com/ps2dev/ps2sdk/blob/ac92a9f657d2e531dd8f060250b07f2a5ac6dea5/iop/system/loadcore/src/loadcore.c) adds `text_start` to the IRX metadata `EntryPoint`, but is mechanism evidence, not proof the game uses that runtime loader revision.

The static relocation comparison does not invalidate the zero-based export. At synthetic base zero, the relocation model produces the original file-backed PT_LOAD bytes followed by zero-filled BSS for all 24 modules; no image byte changes. The Ghidra `.text` blocks also match the raw `.text` bytes. A separate synthetic base `0x00100000` changes 18,020 bytes across these images, but that base was not used for the Ghidra export and is not a recovered runtime allocation. A nonzero base changes encoded address values; this audit does not infer runtime behavior from that comparison.

Setting Ghidra's GP context from `.iopmod.gp + base zero` left all probed memory-block hashes and the function-entry inventory unchanged. It changed three pseudocode hashes versus the earlier fallback context, with no function-signature changes: two THREADMAN functions change a stored `unaff_gp` value to `0xf080`, and one MODLOAD function changes the `_gp_1` symbol label to `_gp_2`. The GP probe reports no GP-based load/store accesses in executable `.text` across the 24 modules. These are decompiler presentation/dataflow changes under a synthetic base-zero context, not changed input instructions or evidence of the runtime GP value.

The most recoverable next static work is to export exact `.text` code-unit and function-body address ranges, classify the residual bytes as instructions, embedded table data, padding, or undefined bytes, and review the 13 metadata-defined entry points first. A separate API-name crosswalk can use the already parsed 166 import libraries and 748 numeric stubs, but it must match library, version, and index before assigning names; imports remain unresolved in this snapshot.

Jev verified the six bounded findings and audited all 13 entry-point extracts with no flagged records (highest `P(wrong)` `0.45`, below the `0.70` threshold). Its one-time priority choice weakly favored the listing-range export (`0.57` versus `0.42` for entry-point boundary recovery; confidence `0.47`). Treat that as a low-confidence planning signal, not a correctness judgment: a listing-range export is the general prerequisite, with the 13 missing entrypoint starts as its first concrete boundary checks. The per-claim results and decision distribution are preserved in [the snapshot](coverage-snapshot-20261004.json).
