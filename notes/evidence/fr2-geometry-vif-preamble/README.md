# VIF preamble and E-stop continuation audit

This bundle narrows the static VU-input investigation to the DMA-buffer helper `FUN_0010f8f8`, the geometry packet writer `FUN_00128e88`, and the VU E-stop / VIF MSCNT continuation around overlay 5. It contains source hashes, bounded receipts and interpretations only; no game routine or emulator was executed.

The raw overlay settles the pair numbering: overlay 5 begins at disassembly byte address `0x2800`, and each VU pair is 8 bytes. Pair 213 at `0x2ea8` is E-marked `nop`; pair 214 at `0x2eb0` is the one-instruction delay-slot `nop`; pair 215 at `0x2eb8` is `xtop vi01`. This pair/address/raw-byte finding supersedes the interim line-count labels 214/215/216 in `jev-verify-e-stop-msc-order-superseded-pair-index.json` and the first screen receipt. The initial Jev verification left the line-count statement at review; the corrected raw bytes are verified with one review disposition retained in `jev-verify-correct-pair-addresses.json`.

The material control-flow correction is the output-buffer order in `FUN_00128e88`: after the current geometry payloads, it writes STMOD 0 and STCYCL 4/4, then MSCNT, then a BASE selected between `0x3aa` and `0x388`, then OFFSET 0. The saved source advances the same `puGpffff9220` cursor after each store. Pinned PCSX2 VIF1 code handles MSCNT by calling `vuExecMicro(idx, -1, false)`. That path latches TOP from the current TOPS before updating TOPS from DBF/BASE/OFFSET; OFFSET itself clears DBF and sets TOPS to BASE when the parser reaches it. Therefore the BASE/OFFSET emitted after this MSCNT do not set the TOP latched by that same MSCNT. The resumed XTOP at pair 215 has a TOP value dependent on TOPS already in effect at MSCNT. The prior inference that this MSCNT continuation necessarily uses the newly emitted `0x388`/`0x3aa` BASE is superseded.

`FUN_0010f8f8` starts an inline CNT tag, puts VIF FLUSHA (`0x13000000`) and DIRECT(2) (`0x50000002`) in the TTE words, then appends one packed GIF A+D write. The GIF register address is `0x4e` (PS2SDK `GS_REG_ZBUF_1`); the qword computed from `DAT_002324fa`, `DAT_002324ec`, and `iGpffff911c` is the GS register data. It is not a DMA REF descriptor. Its function body has no literal STCYCL/STMOD/STROW/BASE/OFFSET/MSCNT command. A bounded VIF1 submitter writes QWC zero at `0x10009020`, TADR at `0x10009030`, and CHCR `0x145` at `0x10009000`, which sets TTE bit 6. The pinned PCSX2 VIF1 chain source transfers the upper 64 bits of a tag when TTE is set. Static follow-through from the later render buffer to a particular submitter/queue remains incomplete.

`FUN_00128e88` writes STROW: after STCYCL 3/1 and the V4-8 transfer segment, it stores `0x30000000` followed by row words `[0x44400000, 0x44400000, 0x44400000, 0]`. If `param_4 != 0`, it later emits another STCYCL 3/1 and STROW `[0x45c00000, 0x45c00000, 0, 0]`. These row updates precede the tail STMOD 0 and STCYCL 4/4; they do not prove that earlier packet data used MODE 0. The later tail sequence is statically established, but the first render iteration's inherited VIF state and runtime dispatch remain open.

The `uVar14` selector values `0x208` and `0x2c8` are not the V4-32 UNPACK destination or a proven buffer base. `FUN_00128e88` first emits V4-32 command `0x6c058000` (NUM=5, TOPS-relative address 0); the selected `uVar14` is data in that packet and also contributes to a later V4-8 command immediate. The tail BASE value is independently selected from `0x3aa` and `0x388` by `uGpffff921c`. These fields have distinct packet roles; this bundle makes no equivalence claim between them.

A conditional MODE/CYCLE path is supported at the builder level. In `FUN_001288b0`, each nonzero-count group at record offsets `+0x1c` or `+0x28` calls `FUN_00128e88` in a loop. `FUN_001ce288` calls `FUN_00128ca0` before `FUN_001288b0` on each loop iteration; if a geometry group runs and another outer iteration follows, that next iteration's explicit V4-32 packet is appended after the prior group's STMOD 0 and STCYCL 4/4 tail. Between them, the visible path appends FLUSHA/DIRECT and GS packets; `0010f8f8`'s computed qword is GS data, not a VIF tag or REF. This proves source-level command-buffer order only, not DMA scheduling or runtime VIF state. The first loop iteration's inherited state, queue boundaries, prior TOPS, and VU consumption remain unresolved.

The prior statement that a BASE/OFFSET in `FUN_00128e88` precedes its MSCNT was wrong; it is retained as superseded in `jev-screen-initial-review.json`. The first screen receipt included an agent-authored parenthetical suggesting that order and received `review`; it is not evidence. An intermediate screen also passed while containing the same incorrect order and pair labels; its outcome is retained only as a superseded receipt. The corrected primary-source screen passed in `jev-screen-primary-sources-corrected.json`. Prior broad jgrep no-hit and hit outcomes remain unchanged; those no-hit results did not establish absence. Exact raw jgrep outputs and argument arrays remain under ignored `.scratch/mesh/codex-root/geometry-vif-preamble/jgrep/`; `jgrep-summary.json` records their hashes, paths, and counts. The explicit STROW findings here come from source-word order and pinned PS2SDK opcode definitions. Earlier provenance in `../fr2-geometry-vu-input-provenance/` is left untouched.

Sony’s VU User’s Manual v6.0 §3.4 / Figure 3-19 defines the single E-bit delay instruction and TPC continuation. The online mirror used for the bounded check is [VU User’s Manual](https://docs.alexrp.com/mips/ee_vu.pdf). PCSX2 source is pinned to commit `81526d4dc7cc70e4ae75abb35a789417456c6d43`; PS2SDK command field definitions and hashes appear in `source-provenance.json`.

No runtime, emulator, GUI, or original game routine was run. This audit proves static command-buffer order and a source-pinned emulator continuation model, not hardware execution equivalence.
