# IOP entry-zero coverage and bounded candidates

This package records a static, offline Ghidra audit of all 24 pinned IOP IRX modules. Coverage exports ran read-only with analysis disabled. Candidate creation and decompilation ran only on a fresh copied database. No module code ran, no C output was committed, and the canonical project was not changed.

The exact per-module code-unit ranges, function-body ranges, block hashes, and references to address zero are in `.scratch/mesh/codex-audit/iop-entry-recovery/coverage/`. The first 13 candidate receipts are in `.scratch/mesh/codex-audit/iop-entry-recovery/candidates-final/`; the wrong-input negative control is in `negative-final/`. The initial compact summary is coverage-and-entry-summary.json (local artifact `../../../.scratch/mesh/codex-audit/iop-entry-recovery/coverage-and-entry-summary.json`). The scripts are [ExportIopCoverage.java](../../../tools/ghidra/experimental/ExportIopCoverage.java) and [CreateIopEntryCandidates.java](../../../tools/ghidra/experimental/CreateIopEntryCandidates.java).

The read-only export used the saved corrected-base-zero project at `/tmp/codex-iop-ghidra-projects/iop-mips-gp-corrected-01`, copied to `/tmp/iop-entry-recovery-projects/iop-entry-audit`. It is the existing Ghidra 12.1.3 database from the earlier 24-module run; no reanalysis was performed. The output preserved 2,241 functions, with exact entry sets and per-function `body_bytes` matching the earlier manifests. All 24 raw `.text` hashes matched their initialized Ghidra `.text` block hashes.

Across the 24 `.text` blocks, 506,336 bytes partition as 488,344 instruction bytes, 2,260 defined-data bytes, and 15,732 undefined bytes. Of the instruction bytes, 469,428 lie in saved function bodies and 18,916 are unowned. These are byte-exact Ghidra listing classifications; they do not validate every instruction's meaning or establish complete original-code recovery.

The parsed `.iopmod` metadata has `entry_address == 0` in 14 modules. `STREAM.IRX` already has a saved function named `start` at zero. Thirteen other modules have a decoded instruction at zero but no saved function there: CDVDMAN, EESYNC, FILEIO, IOMAN, LOADCORE, LOADFILE, MODLOAD, ROMDRV, SDRDRV, SIFMAN, STDIO, SYSCLIB, and TIMEMANI. For each, existing references to address zero are imported `DATA` references from ELF program/section-header structures; no code reference to zero was found. Twelve first instructions are stack-frame `addiu sp,sp,-N`; LOADCORE begins with `mtc0 zero,Status`.

Each of those 13 entries passed a bounded isolated experiment. The script computed a possible body from already-decoded instructions, rejected existing-body overlaps and any body not entirely covered by existing instruction units, then created one provisional `ANALYSIS`-source function in the copy. Each copy gained exactly one function; every pre-existing function entry/name/body row, initialized-memory hash, and instruction/data listing fingerprint remained identical. The STREAM negative control was rejected by the strict input-hash allowlist. The candidate extents are hypotheses, not established function boundaries: LOADCORE's CFG traversal, for example, spans two ranges totaling 1,628 bytes (`0x0..0x23` and `0x30..0x667`). The provisional annotations were kept in the copied database. A later exact-checked run exported that copy as scratch pseudocode, as described below.

The first coverage and candidate receipts predate the raw-section guard additions below; they are retained unchanged as historical artifacts. The strict coverage receipts are under `.scratch/mesh/codex-audit/iop-entry-recovery/strict-coverage/` (24 modules). Initial guarded candidate receipts are under `strict-candidates/`; the final exact-address-set candidate run is under `strict-exact-candidates/` (13 modules). The durable compact index is [index.json](index.json), and [strict-validation-summary.json](strict-validation-summary.json) records input and script hashes, raw ELF metadata fields, per-module results, and claim limits. Strict coverage requires the raw input directory as its second script argument; strict candidate creation requires the exact raw ELF path as its second argument. Both enforce `MIPS:LE:32:default`, compiler spec `default`, ELF32 little-endian `ET=0xff80`/`EM_MIPS`, one executable `.text` section at ELF address zero, `.iopmod` section type `SHT_IOPMOD`, matching declared text length, and a byte-for-byte raw ELF/Ghidra `.text` hash match. The candidate script additionally requires `.iopmod.entry_address == 0`, and its entire proposed body must lie inside `.text`, exactly equal the union of already-defined instruction-unit addresses (both set differences empty), and avoid saved-function body overlaps before it calls `CreateFunctionCmd`.

Fresh strict coverage accepted all 24 modules. The final exact-address-set candidate run on a fresh copy accepted all 13 entry-zero candidates with no body gaps or overhang; CDVDMAN’s candidate body is 148 bytes. Fresh negative controls moved `.text` away from address zero: candidate creation returned `rejected_profile_guard`, while the coverage script failed before creating an output receipt. Decompilation from the exact-checked candidate project produced C in `.scratch/mesh/codex-audit/iop-entry-recovery/strict-exact-decomp/`; all 720 saved functions in those modules generated with zero failures. These are Ghidra pseudocode snapshots, not recovered source or proof of function identity, invocation, semantics, or completeness.

To validate the original historical summary and receipt relationships, run `python3 .scratch/mesh/codex-audit/iop-entry-recovery/summarize.py`; it checks hashes, historical function inventories, text partitions, all 13 no-overlap candidate bodies, and the original wrong-input-control disposition. The strict summary is a separate immutable report and does not rewrite those earlier results.

Jev's initial verification supported the coverage and candidate-preservation claims, and contradicted a deliberately overbroad claim that CFG-derived extents prove the original function boundary or runtime invocation. The initial patch review and final gate escalated (`safe_to_apply` 0.45 and 0.37). A later strict-guard review also escalated (`safe_to_apply` 0.40 overall); keep the scripts experimental. Initial results are in [jev-results.json](jev-results.json), and strict-guard distributions are in [strict-jev-results.json](strict-jev-results.json). These judgments are advisory and do not replace the hash, interval, and state comparisons above.

Root [independently validated](root-validation.json) all 24 raw input hashes, the 13 exact candidate address sets, old function row preservation, initialized-memory and listing preservation, and every hash of the 720 C exports. The full 24-module union has not been freshly exported at this checkpoint. Four old pseudocode files changed: CDVDMAN `0000227c`, FILEIO `000018f0`, LOADFILE `0000134c`, and SIFMAN `00000348`. Every change substitutes the provisional function name for a code-pointer zero in an assignment or comparison. This is a base-zero symbol/null presentation collision, not evidence of a runtime call. The unchanged database function inventory does not imply unchanged pseudocode. [Root Jev verification](root-entry-verification.json) supports the bounded preservation/export statements and contradicts the runtime-call overclaim; the earlier escalated reviews remain in force.
