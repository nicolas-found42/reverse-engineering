# Bounded IOP IRX load and relocation model

`tools/ps2_irx_relocations.py` models the measured ELF32LE MIPS `ET_SCE_IOPRELEXEC` profile for the 24 IRX modules in the pinned executable corpus. It creates a new byte image at a caller-supplied synthetic IOP RAM base, copies the one `PT_LOAD` segment, leaves its BSS tail zero-filled, and applies the observed `R_MIPS_32`, `R_MIPS_26`, `R_MIPS_HI16`, and `R_MIPS_LO16` relocations. It translates the `.iopmod` entry, GP, and module-ID offsets using the same base-plus-offset rule; the `0xffffffff` module-ID sentinel remains absent. The metadata parser exposes the third `.iopmod` word as `gp_offset` and retains `unknown` as a compatibility alias.

This is a bounded static byte model, not an executable loader. It accepts only ELF type `0xff80`, exactly two 32-byte program headers (IOPMOD metadata followed by one zero-based `PT_LOAD`), word-aligned module and segment extents, zero-symbol eight-byte `SHT_REL` entries targeting allocated sections, and the four relocation types observed in this corpus. Each allocated `PROGBITS` section must be wholly file-backed and map at `PT_LOAD.offset + section.address`; `.text` must start at address zero and the load segment's file offset. The `PT_LOAD` file size must equal `.iopmod` text plus data sizes, while memory size must equal text plus data plus BSS. It rejects other ELF profiles, nonzero symbols, malformed sites, unsupported relocation types, nonempty RELA sections, duplicate sites, and HI16/LO16 entries without their observed adjacent pair. The synthetic base must fit the complete memory image inside a 2 MiB address window. This bound is a test placement constraint; it does not establish where the game or PS2SDK allocates any module at runtime.

The source basis is [`loadcore.c` at pinned ps2dev/ps2sdk commit `ac92a9f657d2e531dd8f060250b07f2a5ac6dea5`](https://github.com/ps2dev/ps2sdk/blob/ac92a9f657d2e531dd8f060250b07f2a5ac6dea5/iop/system/loadcore/src/loadcore.c). `ProbeExecutableObject` recognizes the two-header IOP ELF shape; `loadrelelf` adds `text_start` to the metadata entry, GP, and module-ID values, copies `PT_LOAD` bytes, zeroes its remaining memory, then visits `SHT_REL` sections. `ApplyElfRelSection` supplies the four supported arithmetic operations. The checkout's source SHA-256 is `2eb29f11cce431de18f8d5f64c64e4eda22507bfca26487a57b53b63750e0d78`; the upstream repository is under the [Academic Free License 2.0](https://github.com/ps2dev/ps2sdk/blob/ac92a9f657d2e531dd8f060250b07f2a5ac6dea5/LICENSE). The source was screened by Jev (`.scratch/mesh/codex-root/jev/r062-iop-loadcore-source-screen.json`, recommendation `pass`) before use. No upstream code is copied into the permanent model.

The original `ApplyElfRelSection` body was also compiled as a scratch-only C harness and run on synthetic relocation words. The only adaptation replaces the source's 32-bit cast of the destination pointer with an explicit synthetic base parameter, because this host uses 64-bit pointers. Its words matched the Python model for R32, J26, HI16 carry, LO16, BSS R32, and uint32 wrap. Neither this harness nor the Python model executes an original module or entry point. The harness and binary remain in ignored scratch; their hashes and output are recorded in [relocation-model.json](relocation-model.json).

The corpus comparison re-opened all 9 standalone IRX files and extracted the 15 embedded modules using the pinned boundary inventory. All 24 input hashes, PT_LOAD file/memory extents, allocated `PROGBITS` mappings, `.text` zero mappings, `.iopmod` file/memory sums, and relocation counts match the metadata-only inventory receipt. Totals are 2,197 type-2, 9,060 type-4, 6,763 type-5, and 6,763 type-6 relocations (24,783 total); the largest PT_LOAD memory extent is 179,776 bytes. Every module accepted synthetic base `0x1000` under the 2 MiB bound. [relocation-model.json](relocation-model.json) preserves the original nine-test base-profile/native-harness receipt as a historical snapshot. The fresh checks for the added file-mapping guards, including all 24 per-module metadata rows and hashes, are in [relocation-consistency-20261004.json](relocation-consistency-20261004.json); no payload bytes or relocated images are stored here.

Twelve focused synthetic tests cover copy/BSS behavior, the four relocation operations and carry/sign cases, address translation and the module-ID sentinel, uint32 wrap, end-of-window placement, strict-profile failures, malformed/duplicate relocation sites, unsupported types and symbols, HI16/LO16 adjacency, inconsistent `.text` and allocated-PROGBITS mappings, a PROGBITS span beyond `PT_LOAD` file bytes, and a `PT_LOAD` file-size mismatch against `.iopmod` text/data. Run them with:

```sh
python3 -m unittest discover -s tools -p 'test_ps2_irx_relocations.py' -v
python3 -m unittest discover -s tools -p 'test_ps2_irx.py' -v
```

The model establishes static compatibility with the pinned SDK source operations and the measured 24-file profile. It does not prove that this SDK revision is the game's loader, that every module is loaded, that the synthetic base reflects a runtime allocation, that imported APIs resolve, or that any relocated code behaves correctly.
