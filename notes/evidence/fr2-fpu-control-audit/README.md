# Static EE COP1 compare and branch audit

This audit checks the pinned PS2Recomp COP1 compare, BC1 branch, and control-register paths against the Sony EE Core Instruction Set Manual v6.0 and one pinned PCSX2 implementation. It covers measured instruction presence and source behavior only. It runs no original game code, emulator, or hardware.

The pinned PS2Recomp revision is `c5a9d02573410a2085a4b4b831b0b68ba3515440`. Its `C.EQ.S`, `C.LT.S`, and `C.LE.S` translations set or clear FCR31 bit 23 from host `==`, `<`, and `<=` comparisons, preserving other FCR31 bits. The Sony manual specifies those predicates, states that +0 equals -0, and assigns the comparison flag to FCR31 bit 23. PCSX2's pinned FPU implementation also models the condition flag as `0x00800000` and updates that bit for comparisons. For finite supported operands, the inspected predicate and flag behavior agrees with the manual and the software comparator.

`BC1F` and `BC1T` test or invert FCR31 bit 23. `BC1FL` and `BC1TL` are classified as likely branches, with the delay-slot translation emitted only inside the taken branch path. The Sony manual specifies the same condition-bit tests and nullification of the delay slot when a likely branch is not taken. The non-likely path emits the delay slot regardless of branch outcome. In the saved function inventory, the unique instruction counts are 112 `C.EQ.S`, 734 `C.LT.S`, 425 `C.LE.S`, 578 `BC1F`, 174 `BC1T`, 334 `BC1FL`, and 175 `BC1TL`; no `CFC1` or `CTC1` instructions were found.

The valid `CFC1 FCR31` path sign-extends through `SET_GPR_U32`, which constructs the low 64-bit result from `(int64_t)(int32_t)value`, matching the manual. `CTC1 FCR31` masks the stored bits with `0x0183ffff`; the manual says CTC1 transfers the lower 32 bits, while this audit did not establish the EE's reserved-bit write behavior. Neither control-register instruction occurs in the measured inventory, so this remains an out-of-corpus question.

The translator returns zero for `CFC1 FCR0`; pinned PCSX2 returns `0x2e00`. The original Instruction Set Manual-only check did not specify a numeric FCR0 value, and its Jev verification correctly left that claim unsupported. A separate check of Sony's EE Core User's Manual v6.0, printed page 158, Table 8-1, documents bits 15:8 as implementation field `0x2E`, bits 31:16 as zero, and bits 7:0 as a silicon revision byte whose numeric value is unspecified. Therefore, when `CFC1 FCR0` executes, PS2Recomp's all-zero result omits the documented nonzero implementation field. This is a bounded, out-of-corpus field mismatch: the saved inventory contains no `CFC1`, and the evidence does not establish that the complete expected FCR0 value is `0x2E00` for a particular EE revision.

The source and behavior checks do not establish NaN behavior; Sony's manual says the EE FPU does not support NaN. No patch is proposed. ## Audit method and sources

Semantic lookup used `jgrep --json "sets the FPU condition bit from floating point compare instructions" ps2xRecomp/src` from the pinned PS2Recomp checkout. It returned `ps2xRecomp/src/lib/fpu_translator.cpp` lines 12-71 at p=0.76 and lines 72-131 at p=0.93; exact identifiers were then checked with `rg` and read directly. `jgrep` resolved to `/Users/Nicolas/.local/bin/jgrep`.

Firecrawl fetched the Sony Instruction Set Manual PDF and the raw PCSX2 file through `.scratch/mesh/codex-root/firecrawl_fetch.py`; both returned HTTP 200. Jev screened the extracted instruction-manual excerpt (injection .24, substance .99, relevance .98, pass) and the full PCSX2 file (injection .04, substance .98, relevance .97, pass) before factual use. For the addendum, the Sony EE Core User's Manual was opened directly at `https://docs.alexrp.com/mips/ee.pdf`, printed page 158 / Table 8-1; Jev screening returned injection .02, substance .97, relevance .97, pass. Jev verified the three bounded addendum claims (all three verified, zero contradicted/unsupported/needs-review). The prior verification result remains preserved and applies to the earlier instruction-manual-only evidence. Pinned source hashes, source locations, and judgment outcomes are listed in the JSON metadata/receipt files.
