# Overlay-5 consumer of the TOP-relative packet

This supplement records what the static VU instructions establish about the continuation after the E-marked pair. It does not claim that the game executes this stream, that the VIF TOPS state is globally known, or that the selected value is a renderer output pointer.

Overlay 5's saved `.data` base is `0x2800`; pairs are 8 bytes. Raw pair 213 at `0x2ea8` is `nop[e]`, pair 214 at `0x2eb0` is its `nop` delay instruction, and pair 215 at `0x2eb8` is `xtop vi01`. Pair 221 at `0x2ee8` executes `ilw.z vi03,3(vi01)z`, reading the Z component of VU data-memory quadword `TOP+3` into `vi03`. Later instructions use `vi03` as a VU data-memory base: `lq vf15,0(vi03)` at pair 228, `lq vf12,2(vi03)` at pair 229, and `ilw.w vi06,1(vi03)w` at pair 237.

The packet writer's inline CNT packet records the V4-32 command followed by five payload qwords before it patches the CNT QWC and appends the later vertex REF: qword 0 comes from `param_5`; qword 1 repeats the low-byte value from `param_8`; qword 2 combines the preceding 64-bit GIF-tag field with `0x412`; qword 3 is `[count, 0, uVar14, 0]`; qword 4 is the 16-byte `param_6` value. The writer's QWC formula is `ceil((write_cursor - CNT_tag_start)/16) - 1`; at the patch point the span is the 16-byte tag plus 80 bytes of payload, so it yields CNT QWC=5. The first `param_3` REF record is appended after that patch. This establishes that the later REF data cannot shift the earlier qword-3 lane.

Given the packet's stated V4-32 layout, the lane-level static mapping is therefore `uVar14` at TOPS-relative payload qword 3, Z lane. Pair 221 reads `TOP+3.z` into `vi03`; if this same TOPS value is latched by the later MSCNT continuation and VIF's applicable mode/cycle state stores the lanes directly, `vi03` receives the selected `0x208` or `0x2c8` value. The control/data linkage is static and conditional on that VIF state; actual runtime TOPS and all-caller MODE/cycle state remain unproved. The selected values are not named as XGKICK pointers.

The same saved render-loop path gives a conditional prior-tail-to-next-header sequence. In `001ce288`, the `00126c18(4)` preparation call precedes `00128ca0`'s matrix packet, which precedes `001288b0`'s geometry packets. Inside `001288b0`, `00129428` and `001297b8` append FLUSHA/DIRECT and GIF/GS packets before `00128e88` writes its V4-32 header. The saved direct-call closure contains 276 functions; exact command-word scanning finds the STMOD literal `0x05000000` and STCYCL literal `0x01000404` only in `00128e88`. Other nearby `0x50` words are DIRECT commands, not STMOD. For repeated geometry records, the saved order is `00128e88`, record advance `00121420`, then loop back to `00128e88`; there is no explicit STMOD/STCYCL writer between those calls in the closure. Therefore, if those appended packets reach VIF in this one order, the prior geometry tail's MODE=0 and CL=WL=4 remain the explicit state at the next matrix and geometry headers. The first iteration's inherited state and actual DMA/VIF order remain unknown; unmodeled indirect or external state effects are outside this static result.

The four scratchpad vectors have a concrete producer path but no semantic names. Raw calls show `001ce288` passes 4 to `00126c18`; that function calls `00127c00(1)`, which passes output addresses `0x70003160`, `0x700031e0`, and `0x70003220` to `00128518`. It tail-calls `00115560`; the latter stores four 16-byte vectors at the first output base plus offsets `0x30`, `0`, `0x10`, and `0x20`. `00128ca0` later reloads `0x70003160`, `0x70003170`, `0x70003180`, and `0x70003190` into the packet. This proves the producer-to-packet address path, not camera, projection, axis, unit, or other vector meaning.

The saved overlay has XGKICK instructions at `0x2a50` (`vi11`), `0x2b70` (`vi08`), and `0x2e38` (`vi11`), all before the E stop at `0x2ea8`. There is no XGKICK after pair 215 in this overlay. This means this resumed sequence does not itself execute an XGKICK using `vi03`; it does not rule out later code outside this overlay consuming a related value.

An earlier working hypothesis treated all eight vectors in the separate `0x6c080000` matrix packet as caller-provided `param_1` data. The saved source does not support that: only the first four vectors come from `param_1`; the last four come from the separately produced scratchpad block `0x70003160..0x70003190`. That hypothesis is superseded, and no semantic matrix labels are assigned here.

Raw binaries and full disassembly remain in ignored `.scratch`; only bounded instruction anchors, source hashes, and the Jev receipt are kept here.

Root independently checked149 stored EE anchor occurrences at108 unique addresses against both the pinned static export and unique ELF PT_LOAD byte ranges, plus seven VU pairs against original overlay bytes. Only delay-slot underscore text prefixes were normalized. The checker and result retain the earlier wrong0010f9f0 row and two checker-shape failures; neither failure accepted an incorrect row. That mechanism result leaves actual game state conditional.
