# Geometry section and VU consumer audit

**Corrected field map:** the loader copies serialized offsets `+0x08/+0x0c/+0x10/+0x14` into runtime row offsets `+0x0c/+0x10/+0x14/+0x18`. The earlier offset set omitted cumulative source-cursor updates. Its tools, prose, metadata, passing tests, corpus measurements, and Jev receipts are preserved as superseded evidence. Current results and disposition are in [the root correction](root-correction/README.md).

This read-only audit connects a bounded geometry-section parser to one downstream object-processing path. It establishes a loader-derived serialized layout and a parsed-object-to-VU0 transform use at object/float level. It does not identify the six-byte/four-byte planes as vertices, indices, normals, texture references, or prove that those bytes enter a VIF1/VU1 draw packet.

The loader at `FUN_0011ed90` advances 0x34-byte records and reads two unsigned halfword counts at record offsets `+0x1c` and `+0x28`. Each associated variable header has flags at `+0`, count at `+2`, and an optional third halfword. Its payload cursor advances through a 6-byte-per-count plane, optional 20-byte plane selected by flag `0x800`, an always-present 4-byte plane, an additional 4-byte plane unless the third halfword is `0xffff`, and optional 4-byte planes selected by `0x40` and `0x80`; each plane boundary is aligned to 16 bytes. These are serialized layout facts; the plane semantics remain unresolved.

For an exact corpus anchor, `3DDATA/CARS/49COUPE.PS2;1` has SHA-256 `62e3de6688791e6af88d65bebe7156ee2d1f1ec83911316cafddf3173259f381`. Its geometry table begins at byte `933940` with 39 records of `0x34` bytes, geometry headers begin at `935968`, payload begins at `938880`, and the next section begins at `1143232`. The first header has count 64, flags `0xc008`, and third halfword 0. Its measured spans are 384 bytes at `938880` (stride 6), 256 bytes at `939264` (stride 4), and 256 bytes at `939520` (stride 4). Four in-memory mutations of that header (count +1, toggling `0x40`, toggling `0x800`, and changing the third halfword to `0xffff`) were rejected by the existing section parser; see `metadata.json` for the exact failure classes. These are alignment/count falsifiers, not semantic identification tests.

The consumer link is narrower than a complete draw path. In `FUN_0012d4b8`, the code calls `FUN_0011ed90`, stores the parsed object, and looks up `SKYDOME` and `MINI_SKYDOME`. Its later object-processing loop calls `FUN_00121590` on object pointers, reads float fields at offsets `+0x0c`, `+0x10`, `+0x14`, and `+0x18`, then calls `FUN_00113aa8` to build a transform. That helper sends nonzero angle parameters through VU0 `vcallms 0x4d`, the byte VMA `0x268`, and writes a 4-by-4 float transform to an output buffer. This demonstrates a parsed-resource object-to-VU0 transform path. It does not prove those float fields are read from any particular `0x34` geometry plane, nor that the transform consumes a mesh vertex stream.

The evidence stores function entries and narrow source hashes, not whole decompilation files. `jev-consumer-link-verify-01.json` preserves the full Jev request and result. The reviewer verified all four bounded claims; that judgment is advisory and does not replace instruction-level inspection. jgrep independently found the parser behavior and the parsed named-object path, while its scoped search for a geometry-to-VIF packet path returned no matches. The VU transform details were confirmed from the exact saved instructions and C excerpt.

The root-name/expanded-row mapping is now traced in `object-float-provenance-01.md`. The bounded verifier in `tools/verify_object_floats.py` checks the four mapped serialized fields across the 56 archive-pinned model files; see [the corrected corpus receipt](root-correction/corrected-corpus.json). The next falsifiable step is to trace one specific `0x34` geometry payload plane from its loader cursor to a direct consumer read. Plane meaning, vertex/index relationships, VIF1/VU1 submission, and VU0-derived output behavior remain open.

A follow-up trace now ties one exact serialized `expanded_24` row span to the per-name 32-to-36-byte runtime row writer and the scalar inputs consumed by `FUN_00113aa8`. The source fields and finite-value measurements are documented in [object-float-provenance-01.md](object-float-provenance-01.md). This establishes a bounded source-to-transform-input correspondence; VU0 output behavior, plane semantics, and renderer submission remain open.
