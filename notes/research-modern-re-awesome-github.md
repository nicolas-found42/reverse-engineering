# Modern reverse-engineering methods: awesome-list and GitHub findings

Research slice for the Ford Racing 2 PS2 handoff, captured 2026-10-03. The local handoff says the target is a stripped EE ELF accepted by Ghidra's R5900 language, the Ghidra analysis is saved, its Python report-export step failed without PyGhidra, and the custom FILES.HDR/FILES.DAT parser has already extracted and validated all 990 files. Those local facts come from .scratch/HANDOFF-ford-racing-2-re.md (local artifact `../.scratch/HANDOFF-ford-racing-2-re.md`) and [the existing FR2 note](ps2-re-ford-racing-2.md).

## Finding and recommendation

The strongest practical sequence is to finish the existing Ghidra export/function map, correlate string xrefs and likely loader routines with the already-verified archive parser, then ground selected hypotheses in PCSX2's debugger. This uses an R5900 analysis path already demonstrated on this ELF and adds runtime observations where they answer a specific static question. Treat PCSX2 observations as emulator evidence and keep the emulator context attached to each observation.

This order is a Jev decision over five choices with the task's stated preferences and local state supplied: finish_static_then_emulator was selected at 0.97; the two explicit requirements (target fit and immediate value) were both judged supported. The competing ideas were format-spec-first (0.03), tracing-first, binary-diff-first, and replacing Ghidra with symbolic execution. See the judgment record linked below.

Ghidra's SLEIGH documentation explains its useful abstraction: processor instruction encodings map to assembly and p-code semantics, which support processor-independent data-flow analysis and decompilation. The local extension, [Ghidra Emotion Engine Reloaded](https://github.com/chaoticgd/ghidra-emotionengine-reloaded), supplies PS2 Emotion Engine and VU support; the handoff records successful use of r5900:LE:32:default with this game. [SLEIGH language reference](https://ghidra.re/ghidra_docs/languages/html/sleigh.html).

Dynamic methods need a target-specific support check. [PCSX2's debugger](https://pcsx2.net/docs/advanced/debugger/) explicitly supports the R5900 layout for the Emotion Engine, instruction disassembly from memory, register views, memory search, and symbol import from the boot ELF or external files. That makes it a direct runtime counterpart to the existing Ghidra analysis. [Frida Stalker](https://frida.re/docs/stalker/) is a useful modern tracing design and can follow execution at function, block, and instruction granularity, but its current documented targets are AArch64, Intel 64, and IA-32. R5900 is not listed. It is therefore not a ready-made way to instrument this EE binary. A custom port would be a separate project, not a quick substitute for the emulator debugger.

The ELF is stripped, so names and types remain hypotheses until supported by cross-references or runtime state. |

| Cross-binary similarity | Google's [BinDiff concepts](https://github.com/google/bindiff/blob/main/docs/concepts.md) describe function and basic-block matching over flow/call graph structure, instructions, and references. | Useful if a second FR2 region/build/port or close executable becomes available. No comparable second FR2 ELF is in the handoff, so it ranks low as today's first action. A match is evidence of similarity, not a recovered semantic name. |
| Generic game archive extraction | [QuickBMS's project page](https://aluigi.altervista.org/quickbms.htm) describes a script-based extractor/reimporter and parser for game archives/formats. | Useful for checking existing scripts as leads when a game/format match is independently established. This research did not find a Ford Racing 2 recipe; generic coverage must not be mistaken for FR2 support. Current parser results are stronger for this exact disc. |

## Recent research: useful design lessons, bounded transfer

Two recent arXiv papers support useful evaluation habits, with important platform limits. [Superset Decompilation (arXiv:2603.28002)](https://arxiv.org/abs/2603.28002) describes Manifold as a modular, provenance-guided approach that retains competing interpretations instead of committing early. Its reported evaluation is on Linux ELF/coreutils, not R5900, so transfer the provenance and ambiguity-management idea, not its quality claims. [CODEFUSE-DEBENCH (arXiv:2605.29490)](https://arxiv.org/abs/2605.29490) evaluates decompiler output along readability, recompilability, and behavioral functionality, including differential tracing. Its 640-binary benchmark is not a PS2 benchmark. For FR2, the practical analogue is to assess a recovered routine separately for readable pseudocode, structural consistency, and agreement with observed emulator behavior; do not treat plausible C as proof.

The papers were found through Firecrawl's arXiv research search and checked against the arXiv abstracts. The abstracts are primary-source evidence for paper scope and reported method, not independent reproduction of the results.
