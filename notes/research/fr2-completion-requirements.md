# What remains to complete the Ford Racing 2 PAL reconstruction

Research snapshot: 2026-10-08. The controlling target is [issue #5](https://github.com/nicolas-found42/reverse-engineering/issues/5), which requires a source-built, byte-exact reconstruction of attributed game-owned EE and IOP ranges, eight byte-exact VU reassemblies with caller/interface maps, and consumer contracts for every required asset family. A full retail ELF hash is not required because open-source SDK substitutes intentionally differ; substitute bytes never count as matched. The permitted behavioral oracle has its own status and evidence, separate from static matching. These are the settled project decisions in [ADR-0001](https://github.com/nicolas-found42/reverse-engineering/blob/c65ea3771ec26b65e47216219a999cfcb88db85c/docs/adr/0001-completion-target.md), [ADR-0002](https://github.com/nicolas-found42/reverse-engineering/blob/c65ea3771ec26b65e47216219a999cfcb88db85c/docs/adr/0002-headless-execution-permitted.md), and [ADR-0003](https://github.com/nicolas-found42/reverse-engineering/blob/c65ea3771ec26b65e47216219a999cfcb88db85c/docs/adr/0003-open-source-only.md).

## Suggested dependency order (inference from the criteria)

The order below is a dependency recommendation, not a project promise or time estimate. The underlying dependencies are stated in issue #5 and the open child issues [#8 compiler](https://github.com/nicolas-found42/reverse-engineering/issues/8), [#9 linker](https://github.com/nicolas-found42/reverse-engineering/issues/9), [#11 first slice](https://github.com/nicolas-found42/reverse-engineering/issues/11), [#12 substitutes](https://github.com/nicolas-found42/reverse-engineering/issues/12), [#13 VU](https://github.com/nicolas-found42/reverse-engineering/issues/13), [#14 oracle](https://github.com/nicolas-found42/reverse-engineering/issues/14), [#15 assets](https://github.com/nicolas-found42/reverse-engineering/issues/15), and [#16 IOP](https://github.com/nicolas-found42/reverse-engineering/issues/16).

1. **Establish a bounded ownership decision and extend the map iteratively.** Start with one small source/build unit whose code and data boundaries can be supported under ADR-0005, cross-checking source-path leads against actual consumers and SDK provenance. Record its identity, address ranges, evidence and falsifier. A first slice needs an evidenced local partition; the entire 3,507,048-byte inventory need not be resolved before attempting it. Extend attribution and discovery dispositions alongside reconstruction, then require complete, disjoint coverage with no blocking mixed ranges for final AC04 acceptance. This local-first ordering is an engineering recommendation; the complete partition is the specification requirement.
2. **Turn tool experiments into reproducible matching profiles.** Continue EE compiler probes beyond the one-function discriminator, establish the allowed pinned IOP profile, and separately validate GNU linker placement/relocations/zero-fill. Compiler output and linked address placement are separate variables: GNU ld documentation confirms its scripts control section mapping and memory layout ([GNU ld scripts](https://sourceware.org/binutils/docs/ld/Scripts.html)). Keep a substitute labeled as a substitute; do not call an exploratory unique function match a pinned original compiler.
3. **Complete one vertical slice.** Select a small, nonempty, evidenced game-owned range; write reconstruction source by hand; compile, link/place, produce provenance and compare exact bytes. Add a mutated source/output negative control. This is AC07 and the acceptance target of issue #11.
4. **Integrate the declared dependency/substitute surface, then scale EE.** Reuse the existing pinned PS2SDK source-build bootstrap, preserve per-component licenses, identify the actual interfaces and ranges it must satisfy, and link the reconstructed EE output. Then resolve ABI/type/data/discovery gaps as source units are added until AC08–AC12 pass. Upstream PS2SDK separates EE and IOP components, but a port collection may have heterogeneous licenses; verify each selected dependency instead of assuming the top-level SDK license covers all add-ons ([PS2SDK README](https://github.com/ps2dev/ps2sdk/blob/master/README.md), [ports license note](https://github.com/ps2dev/ps2sdk-ports/blob/master/COPYING)).
5. **Repeat the attributed build-and-match process for IOP modules.** Per module: pin identity, partition game/SDK ranges, establish compiler/linker and imports/exports/relocations, reconstruct and compare game-owned ranges, and document EE/IOP RPC or shared-buffer handoffs. This produces AC13–15 and all 24 declared module outputs.
6. **Complete the independent VU and asset contracts; track behavior separately.** VU encoding already passes; finish entry/state mapping. Build an archive-derived family and variant catalog, trace consumers for audio/PTG/models/text/UI/config/texture/mips and record opaque fields only when consumer behavior supports that claim. In a separate behavioral workstream, establish a strict no-window/no-display/no-audio/focus runner and compare declared scenarios when access permits. A headless emulator command option that only hides the main window is not enough. Missing runtime evidence must remain visible in the behavioral report and does not reduce static matched-byte credit or negate an otherwise passing static reconstruction.
7. **Re-run static acceptance from clean inputs and hand off.** Add missing negative/incomplete fixtures, run two fresh builds, the full suite/IP rails, and the real-corpus aggregate at a clean source revision. Ensure every reconstruction criterion links current receipts and every remaining unresolved static item has a falsifier; show AC25–AC26's independent readiness/coverage status without presenting it as static proof. Only the aggregate's exit 0 for the reconstruction criteria supports static completion and final ticket/map updates.

## What counts as falsifying progress claims

- A matching byte count is false if its range is mixed/unresolved, substitute, excluded without evidence, absent from the full denominator, or supplied by copied retail bytes. [ADR-0005](https://github.com/nicolas-found42/reverse-engineering/blob/c65ea3771ec26b65e47216219a999cfcb88db85c/docs/adr/0005-game-owned-sdk-boundary.md) keeps loadable sections mixed until a measured range split is justified.
- An “exact compiler identified” claim is false if based only on one exploratory probe, lacks candidate/source/tool hashes and flags, or is not tested on discriminating attributed units. Current receipt explicitly says AC05 incomplete.
- A “whole IOP rebuilt” claim is false if a module is only inventoried, imports are parsed without rebuild/match, or synthetic link bases are described as observed runtime addresses. The IOP evidence README states these limits.
- A “VU complete” claim is false if it equates eight byte round-trips with entry points, data flow, scheduling or hardware behavior. AC17 remains separate.
- An “asset family complete” claim is false if it covers headers or selected examples but omits archive variants or actual consumers. Asset contracts must bind to corpus profile and loader/consumer evidence.
- A “headless verified” claim is false if it uses `-nogui` alone, hides a window while still using a display server, emits audio, steals focus, or does not refuse UI-capable setups before execution. PCSX2 documents `-nogui` only as hiding its main window.
- A “static reconstruction complete” claim is false if a required reconstruction criterion is incomplete, test CI is substituted for real-corpus acceptance, a nonempty game-owned denominator is missing, or the final real-corpus aggregate does not exit 0. Separate incomplete behavioral-oracle evidence must be disclosed but is not itself a static byte-match failure.

## How Jev and TypeSafe can support the work

The following workflow is a design recommendation, not an implemented new integration. TypeSafe's [building guide](https://docs.typesafe.ai/concepts/how-to-build-with-system-one.md) assigns deterministic execution and control flow to code and gives the model narrow structured questions. Its [citation-check cookbook](https://docs.typesafe.ai/cookbooks/citation_check.md) demonstrates checking whether source context supports a claim. Applying those patterns here means storing a bounded evidence record for each unit, range decision, dispatch domain or asset profile, then asking semantic questions against that record.

| Job | Useful judgment | What establishes acceptance |
|---|---|---|
| Find relevant evidence for a unit or consumer | Rerank retrieved source-map, call-site, SDK-source and loader candidates; keep a no-match result available. | Recorded corpus identities and inspectable reference/call evidence; relevance alone assigns no ownership. |
| Compare a proposed meaning or ownership claim with evidence | Verify one claim at a time; preserve supporting, contradicting and silent evidence. | A recorded ADR-compatible range or contract decision, with boundaries and falsifier. |
| Select a named value or source span | Generate candidates with parsers/regex, select among them, then audit the copied value. | Code checks addresses, sizes, types, hashes and bounds; the selected text remains tied to its source. |
| Triage the next unresolved investigation | Score useful dimensions separately or assess a bounded hypothesis; use the task graph and fixed criteria to choose work in code. | An executed experiment that distinguishes the hypotheses, followed by independent review. |
| Check a completion statement | Verify that the claimed unit/profile pass is supported by current receipts and source revision. | Real source builds, exact comparisons, negative/incomplete controls and the aggregate status policy. |

Each work record should identify the target, corpus/revision, relevant code/data spans, source/build inputs, precise claim, assumptions, contradicting evidence, deterministic checks, status, and next falsifier. Independent claim questions can be batched over the same record. Question answers and probability distributions should be retained separately from the fixed acceptance rules. These suggestions follow TypeSafe's [building guide](https://docs.typesafe.ai/concepts/how-to-build-with-system-one.md) and this project's [evidence/ledger requirements in issue #5](https://github.com/nicolas-found42/reverse-engineering/issues/5).

For example, a reasoner can propose that a wrapper's buffer field is a byte count. Jev can check whether the cited callers and consumers actually support that claim. A parser and mutation tests must still establish offsets, units, bounds and failure behavior. Compiler and linker execution must establish the output bytes. That separation prevents a persuasive semantic judgment from becoming unsupported numerical or matching credit.

TypeSafe's [Jev 1.13 limitations](https://docs.typesafe.ai/model-jaggedness/jev-1.13.md) explicitly warn about numerical precision, low-level assembly/binary questions and multi-hop indirection. Use parsed facts and bounded questions; route difficult instruction semantics, ABI conflicts and unresolved dataflow to a reasoning model or specialist with the concrete evidence. Its [confidence documentation](https://docs.typesafe.ai/confidence.md) defines confidence from probability-distribution concentration. Treat it as an uncertainty signal, not a replacement for a byte comparator or a scope decision. Thresholds should be evaluated on representative labeled project cases, including known overclaims, missing evidence and contradictory consumers; cookbook demonstration thresholds are not a measured guarantee for PS2 reverse engineering.

The practical loop is: choose an evidenced unit → construct a precise hypothesis/source change → execute the bounded build or decoder experiment → retain deterministic results → verify the resulting claim → update the recorded decision and task graph. A failed experiment produces a narrower next question; it does not authorize changing the denominator or acceptance criterion. Issue #5 already requires Jev escalations to remain visible and says factual acceptance rests on deterministic checks and independent review.
