# Modern reverse engineering methods, applied to Ford Racing 2

Research date: **2026-10-03**, America/New_York. This report surveys current methods and gives a practical research plan for the stripped PS2 Emotion Engine executable and extracted assets in this workspace. Recommendations are analyst inferences from the cited evidence; tool capabilities and paper results are source-backed facts. No game-code recovery, emulator experiment, or AI-decompiler performance on this game was performed during this research phase.

## Recommended direction

Continue the existing processor-aware Ghidra analysis, expose its evidence in a useful function/reference report, and use PCSX2 observations to resolve selected loader and asset-layout questions. Formalize formats after their boundaries and behavior survive corpus-wide checks. Use AI and similarity models to propose interpretations and prioritize inspection; retain addresses, raw instructions, data offsets, and execution observations behind every accepted interpretation.

This recommendation follows the local handoff (local artifact `../.scratch/HANDOFF-ford-racing-2-re.md`): analysis was saved, report export failed at the Python launch mode, and archive extraction already succeeded for 990 files. The existing R5900 extension is a stronger starting point than substituting a generic MIPS tool. Ghidra's SLEIGH language maps instructions into assembly and p-code, and the [Emotion Engine extension](https://github.com/chaoticgd/ghidra-emotionengine-reloaded) provides the PS2-specific processor path. [SLEIGH reference](https://ghidra.re/ghidra_docs/languages/html/sleigh.html).

The tools strand's bounded Jev decision selected static analysis followed by emulator validation at probability **0.97**. This is a preference judgment over measured local state, not a proof that a loader has been identified. The earlier handoff's workstream order remains the starting point; this report adds methods and validation criteria rather than claiming those workstreams are complete.

## Methods worth combining

| Method | What the primary sources establish | How to apply it here; limits |
| --- | --- | --- |
| Processor-aware static analysis and IR | SLEIGH specifies instruction encodings and semantics through p-code; the EE extension supplies PS2 support. [Ghidra](https://ghidra.re/ghidra_docs/languages/html/sleigh.html), [EE extension](https://github.com/chaoticgd/ghidra-emotionengine-reloaded). | Export functions, callers, string/data references, basic blocks, and call targets from the saved project. Follow `files.hdr`, decompression, and CD/IRX references into a loader map. A disassembly label is a hypothesis until its use supports it. |
| Emulator observations and controlled changes | PCSX2 documents separate R5900/R3000 debugger targets, registers, memory searches, symbol import, function scanning, and hashes for overwritten functions. [Debugger guide](https://pcsx2.net/docs/advanced/debugger/). | Map static names into runtime symbols; inspect loader input/output buffers and registers at a reproducible load event. Preserve the disc identity, event, addresses, and bytes. Hashing is particularly relevant if an overlay overwrites code. This phase did not run the game. |
| Declarative binary-format descriptions | Kaitai compiles declarative `.ksy` descriptions into parsers; ImHex's Pattern Language describes and visualizes structures. [Kaitai guide](https://doc.kaitai.io/user_guide.html), [ImHex](https://github.com/WerWolv/ImHex), [pattern examples](https://github.com/WerWolv/ImHex-Patterns). | Convert measured HDR/DAT, MSH, PTG, and model-tree boundaries into executable descriptions. Keep unknown fields unknown. Require exact boundary/length checks over the entire relevant corpus before assigning semantics. |
| Binary diffing and function similarity | BinDiff compares function/basic-block structure, instructions, and references. [Concepts](https://github.com/google/bindiff/blob/main/docs/concepts.md). Research also studies semantic embeddings and inlining-aware matching below. | Useful when a comparable region/build, sibling executable, or appropriate library corpus becomes available. The handoff supplies no second FR2 ELF. Similarity is a lead, not a recovered name or proof of equivalence. |
| Symbolic execution | angr describes symbolic inputs and branch constraints for exploring execution paths. [Symbolic execution](https://docs.angr.io/en/latest/core-concepts/symbolic.html). | Potentially useful for a small isolated parser/function after its instruction semantics, ABI, and environment have been modeled. The retrieved evidence does not establish faithful R5900/MMI/VU support, so replacing the current analysis with angr is unsupported. |
| Binary-only coverage-guided testing | AFL++ QEMU mode collects edge coverage through user emulation for binaries that cannot be rebuilt; that mode is documented as Linux-only. Unicorn mode requires an explicit code/memory/register/input harness. [QEMU mode](https://github.com/AFLplusplus/AFLplusplus/blob/stable/qemu_mode/README.md), [Unicorn mode](https://github.com/AFLplusplus/AFLplusplus/blob/stable/unicorn_mode/README.md). | First validate reconstructed host parsers with bounded mutations. Original EE routine fuzzing would require a demonstrated backend and a captured execution context. Neither generic QEMU user mode nor a Unicorn mention establishes PS2 system emulation. |
| Dynamic binary instrumentation | Frida Stalker documents execution tracing for AArch64, Intel 64, and IA-32. [Stalker documentation](https://frida.re/docs/stalker/). | Useful as a modern tracing reference and for supported host-side programs. R5900 is not among those documented targets. Instrumenting emulator host code also requires a mapping back to guest instructions; it is not automatically an EE trace. |
| AI-assisted decompilation and type inference | The papers below provide concrete methods and bounded benchmarks. | Supply structured CFG/call/type context. Keep generated names, pseudocode, and layouts as candidates. Check structural consistency and behavioral observations independently. The inspected evidence does not establish FR2 or EE instruction fidelity. |

The practical change from an ad-hoc workflow is to keep a small evidence bundle per hypothesis: source bytes, addresses, exact reads/writes, the proposed interpretation, counterexamples, and the checks that would falsify it. For instance, a guessed record length must explain every record boundary, not merely one visually plausible sample. That is a proposed workflow for this corpus, rather than an externally measured result.

## Research papers and what transfers

The paper strand screened **52 discovery candidates** from five Firecrawl paper-index query framings, inspected eleven selected studies, and retained ten detailed studies. Two additional papers were inspected at abstract level in the tools strand. These are author-reported methods and evaluation scopes; no paper experiment was reproduced here. Exact numerical claims that received uncertain verification are excluded from the recommendations.

| Study | Source-backed contribution and evaluation boundary | Transfer to this project |
| --- | --- | --- |
| [LLM4Decompile](https://arxiv.org/abs/2403.05286); [authors' code](https://github.com/albertan017/LLM4Decompile) | End-to-end decompilation and refinement of Ghidra output. Training scope includes GCC-compiled C functions on x86 Linux; evaluations include HumanEval-Decompile and ExeBench. | A baseline for hypothesis generation and output refinement. Its reported results do not estimate PS2 performance. |
| [ReF Decompile](https://arxiv.org/abs/2502.12221) | Replaces raw jump-target addresses with labels and adds function-call context to recover type/missing-variable information. | Normalize branch targets while preserving the address-to-label mapping; include callees rather than feeding an isolated instruction wall. |
| [HELIOS](https://arxiv.org/abs/2601.14598) | Hierarchical control-flow/call-graph context and optional compiler feedback. Tests x86, ARM, and MIPS families and separates compilation/linking/functional measures. | Export graph context and test interpretations separately. “MIPS” does not establish R5900 extensions, VU semantics, or the EE environment. |
| [Decompile-Bench](https://arxiv.org/abs/2505.12668) | A large collection of binary/source function pairs intended to improve evaluation on real project code. | Check train/test separation, compiler/build variation, and benchmark relevance before accepting general source-recovery claims. Dataset size is not architecture coverage. |
| [Cross-Inlining Binary Function Similarity Detection](https://arxiv.org/abs/2401.05739) | CI-Detector explicitly models different inlining patterns instead of assuming one source function maps cleanly to one binary function. | When comparing builds, consider merged/split/inlined functions. Avoid forcing one-to-one matches on optimized code. |
| [VEXIR2Vec](https://arxiv.org/abs/2312.00507) | Uses normalized VEX IR representations and embeddings for binary similarity; evaluation includes x86 and ARM. | Semantic normalization may help comparison. First prove a faithful EE translation path; the paper's evaluated targets do not establish one. |
| [CFG2VEC](https://arxiv.org/abs/2301.02723) | Combines function-call and control-flow graph context. The package dataset includes amd64, armel, i386, and mipsel. | Offers graph-based candidates for function names/matches. Generic mipsel data does not validate EE/MMI/VU coverage. The disputed performance figure is omitted. |
| [Practical Type Inference / XTRIDE](https://arxiv.org/abs/2603.08225) | Grounded type prediction through n-gram contexts and a closed vocabulary. Its discussion distinguishes recurring known types from novel type/layout synthesis. | Consider a known SDK/library vocabulary as a triage source; recover proprietary game structures from actual field accesses and buffers. The uncertain compound accuracy claim is omitted. |
| [BinPRE](https://arxiv.org/abs/2409.01994) | Uses binary execution information to infer protocol-field formats/semantics and evaluates guided protocol fuzzing. | Borrow input-consumption tracing and hypothesis testing for asset parsers. Network message experiments do not establish game-file support. |
| [NetLifter](https://arxiv.org/abs/2305.11781) | Infers protocol formats from static parser-implementation analysis. | Trace offset/length predicates in loader code and reconcile them with asset boundaries. Its parser implementation setting differs from a stripped PS2 executable. |

[Superset Decompilation](https://arxiv.org/abs/2603.28002) describes retaining competing interpretations with provenance; [CODEFUSE-DEBENCH](https://arxiv.org/abs/2605.29490) distinguishes readability, recompilability, and functionality, including differential tracing. These two sources were checked at abstract level. The useful design ideas are preserving ambiguity and separating evaluation dimensions; stronger implementation or platform claims would require deeper inspection.

## A concrete sequence for the game

1. **Expose the saved static evidence.** Repair the exporter with Java GhidraScript; export all functions and the relevant string/data xrefs, plus disassembly and call context for their enclosing functions. The original Python exporter only printed the first 200 functions. Completion means a saved report from the already-analyzed ELF, with reproducible addresses and no report-script failure.
2. **Build a loader hypothesis map.** Trace `files.hdr`, `files.dat`, `inflate`, `cdrom0`, and file-system diagnostic references. Correlate actual loads/strides/shifts with the measured 28-byte records, segment table, 2048-byte chunks, and decompression wrapper. Record tentative function names separately from verified behaviors. Completion means explaining a real input-to-buffer path, not only finding an interesting string.
3. **Use a runtime oracle for specific unknowns.** After configuring PCSX2, reproduce one asset-loading event and inspect the relevant buffers, arguments, and consumers. Export/import symbols to connect the two views. For overlays, distinguish code versions and use overwritten-function information. Completion means a captured, reproducible observation supporting or rejecting a named static hypothesis.
4. **Make format hypotheses executable.** Express stable structures in a declarative schema or the existing parser; test all relevant files, exact boundaries, and expected relationships. Use controlled mutations to expose overfit assumptions. Keep geometry, codec, and text-grammar unknowns explicit until consumer behavior or multiple samples establish their meaning.
5. **Add AI or similarity on top of the evidence.** Provide the function's graph, callees, data references, known structures, and observed inputs/outputs. Rank proposed names/behaviors with Jev and verify the resulting claims against the actual bundle. Add a second build/library corpus only when available. Acceptance requires structural and behavioral evidence; readable pseudocode alone is insufficient.

These are research recommendations, not implementation results. The handoff's interrupted Ghidra export is still outstanding because the user steered this phase to researching methods.

## Jev and TypeSafe workflow, including observed failures

Jev was used for intake screening, semantic ranking, method classification, bounded decisions, source reconciliation, extracted-value audit, claim verification, patch review, and the final completion gate. Fetched content remained task data. A `review` screen prompted inspection; `skip` content was not used. Review and operational failures were recorded instead of being silently promoted to acceptance.

The saved strand summaries and root journal account for **at least 160 completed Jev requests**, including **at least 126 source-screening calls** and the eight live SDK requests. The SDK requests alone contained 24 independent typed questions; ranking/classification/verification calls also batched multiple judgments. These are request and judgment counts, not independent factual confirmations. The tools strand retains compacted screen totals; the paper strand and root retain fuller probability records. Token totals are partial across differently compacted logs, so no exact overall dollar cost is asserted.

For reusable research, retain the source URL/text, screen disposition, claim, selected evidence span, full probability distribution, decision thresholds, action, and later deterministic check. Give independent questions the same relevant state together, then gather new evidence when one result changes the next question. This follows [TypeSafe's building guide](https://docs.typesafe.ai/concepts/how-to-build-with-system-one.md). The [citation cookbook](https://docs.typesafe.ai/cookbooks/citation_check.md) checks normalized quote presence deterministically before checking whether its context supports a claim. Confidence describes the returned distribution; a narrow documentation test does not calibrate a model on game-code interpretation. [Confidence documentation](https://docs.typesafe.ai/confidence.md).

A rerunnable experiment is saved as [research_jev_battery.py](../tools/research_jev_battery.py), with [failure-path checks](../tools/test_research_jev_battery.py). It uses **typesafe-sdk 0.7.2**, model `typesafe/jev-1.13`, the existing `OPENROUTER_API_KEY`, and `https://openrouter.ai/api`. The official [OpenRouter compatibility guide](https://openrouter.ai/docs/guides/community/typesafe-sdk) establishes those API settings and warns that the SDK's model-listing response differs from OpenRouter's. No credentials were saved in the fixture or results.

The false controls included DWARF support, a documented debugger REST API, a separate Noul confidence field, and unchanged SDK model listing. This is a small smoke test.
